## Сырые данные и чистка

### 1. Сколько строк в `tickets`, сколько в ней разных номеров обращений и сколько строк в `clean`? Куда делись строки?

**Ответ:** 7033 строки, 6760 разных номеров, в `clean` тоже 6760. Разных строк ровно 273 — столько же, сколько «лишних». Коллега убрал полные дубликаты: одна и та же строка выгружена по два раза (похоже, система отдаёт обращение ещё раз при каждом изменении статуса). В `clean` от каждого обращения осталась одна копия.

```sql
SELECT COUNT(*) FROM tickets;
SELECT COUNT(DISTINCT id) FROM tickets;
SELECT COUNT(*) FROM clean;
-- сколько строк записаны дважды полностью, одинаково во всех полях
SELECT COUNT(*) FROM (SELECT id FROM tickets GROUP BY id HAVING COUNT(*) > 1);
```

### 2. Каналы в `tickets` и в `clean`. Что коллега исправил?

**Ответ:** В сырых данных канал «чат» записан двумя способами: 'чат' (2711) и с большой буквы 'Чат' (163). Коллега привёл 'Чат' к нижнему регистру — в `clean` чат одна группа, 2770 обращений. Остальные каналы он не трогал, их числа отличаются от `tickets` только из-за удалённых дубликатов.

```sql
SELECT channel, COUNT(*) FROM tickets GROUP BY channel ORDER BY 1;
SELECT channel, COUNT(*) FROM clean GROUP BY channel ORDER BY 1;
```

### 3. Темы в `tickets` и в `clean`. Как в сырых данных записана пустая тема? Что сделал коллега? Всё ли он исправил?

**Ответ:** Пустая тема в сырых данных — пустая строка '' (287 строк). Коллега заменил её на текст 'без темы' (в `clean` таких 278). Но не всё: ещё 157 строк содержат слово 'NULL' — это четыре буквы, а не отсутствие значения, и коллега их пропустил: в `clean` 'NULL' так и остался отдельной темой (152). Поле `topic` вообще не бывает настоящим NULL — проверено ниже.

```sql
SELECT topic, COUNT(*) FROM tickets GROUP BY topic ORDER BY 2 DESC;
SELECT topic, COUNT(*) FROM clean GROUP BY topic ORDER BY 2 DESC;
SELECT COUNT(*) FROM tickets WHERE topic IS NULL;
```

### 4. Даты: сколько строк в формате `ДД.ММ.ГГГГ` и в другом? Сколько обращений «после 1 апреля», если сравнить даты в `tickets` как есть, и сколько по `period` в `clean`? Какой период охватывает выгрузка?

**Ответ:** Формат ДД.ММ.ГГГГ — 2119 строк, остальные 4914 уже лежат в ГГГГ-ММ-ДД. Если сравнивать даты в `tickets` как строки ('2025-04-01'), «после» получается 3337 — но это неверно: у строк в формате ДД.ММ.ГГГГ день стоит в начале, и апрельские даты вида '05.04.2025' такое сравнение не пропускает (в этот формат попадают только даты до 12 числа месяца). Коллега переписал формат и получил по `period`: «до» 3211, «после» 3549. Выгрузка охватывает январь–июнь 2025 (от 2025-01-01 до 2025-06-30), то есть в сырых данных июнь идёт вторым числом — тот же подвох ломает любые фильтры по датам напрямую.

```sql
SELECT COUNT(*) FROM tickets WHERE created_at LIKE '__.__.____%';
SELECT COUNT(*) FROM tickets WHERE created_at NOT LIKE '__.__.____%';
-- «после апреля» наивным сравнением строк и по period коллеги
SELECT COUNT(*) FROM tickets WHERE created_at >= '2025-04-01';
SELECT period, COUNT(*) FROM clean GROUP BY period;
SELECT MIN(created), MAX(created) FROM clean;
-- месяцы в формате ДД.ММ.ГГГГ: видно, что дни доходят только до 12
SELECT substr(created_at, 4, 2) AS month, COUNT(*)
FROM tickets WHERE created_at LIKE '__.__.____ __:__' GROUP BY month ORDER BY month;
```

## Пустые значения

### 5. Сколько обращений бот закрыл сам и у скольких из них нет сотрудника? Что значит пустой сотрудник? Что стало с остальными?

**Ответ:** Бот закрыл сам 1667 обращений, из них у 1570 нет сотрудника (`agent_id IS NULL`) — это нормальный случай: обращение закрыто без человека, поэтому `handle_min` там тоже пусто (проверено: человек не появился ни на одном). Остальные 97 «закрытых» формально ведутся сотрудником: 93 со статусом 'решено', 1 'закрыто без ответа', 3 вообще 'в работе'. Похоже, бот закрыл их по базе знаний, а в системе обращение осталось висеть на исполнителе; три «в работе» — прямое противоречие: бот поставил «решено», а статус не закрыт. Пустой сотрудник также означает, что коллега превратил пустые строки сырой выгрузки в настоящий NULL. Все остальные обращения (`передал` — 1021 и где бота не было — 4072) ведутся сотрудниками, NULL среди них не встречается.

```sql
SELECT bot_result, COUNT(*) FROM clean GROUP BY bot_result;
SELECT COUNT(*) FROM clean WHERE bot_result = 'закрыл' AND agent_id IS NULL;
-- что за 97 закрытых с сотрудником
SELECT status, COUNT(*) FROM clean WHERE bot_result = 'закрыл' AND agent_id IS NOT NULL GROUP BY status;
-- у всех ли закрытых без сотрудника пусто время обработки
SELECT COUNT(*) FROM clean WHERE bot_result = 'закрыл' AND agent_id IS NULL AND handle_min IS NOT NULL;
-- есть ли NULL-сотрудник вне закрытых ботом
SELECT COUNT(*) FROM clean WHERE agent_id IS NULL AND bot_result != 'закрыл';
```

## Нумерация

### 6. Сколько номеров обращений пропущено? Сколько до 1 апреля и сколько после? Что это может значить для выводов?

**Ответ:** Номера в выгрузке идут от 1 по 6947, всего 6760 разных — значит, 187 номеров отсутствуют: 32 до 1 апреля и 155 после (вдвое больше). Пропуски после запуска бота легко объяснить фильтром при выгрузке («галочки по умолчанию»), но можно и тем, что часть обращений бот закрыл так, что они не попали в выгрузку вовсе. Поэтому доля закрытых ботом 62% по этой выгрузке — верхняя граница, а не факт: знаменатель неполный. Сравнение «до/после» опирается на выборку, состав которой мы не контролируем.

```sql
SELECT MAX(num) - MIN(num) + 1 AS last_first, COUNT(*) FROM clean;
SELECT MAX(num) - MIN(num) + 1 - COUNT(*) AS gaps FROM clean;
-- пропуски отдельно по периодам: считаем дыры внутри каждого диапазона
SELECT period, MAX(num) - MIN(num) + 1 - COUNT(*) FROM clean GROUP BY period;
SELECT MIN(num), MAX(num) FROM clean;
```

## Бот

### 7. После 1 апреля: в каких каналах работает бот? Сколько он закрыл сам и сколько передал человеку?

**Ответ:** Бот работает во всех трёх письменных каналах — чат (922 закрыл, 502 передал), почта (478/353) и форма (267/166). Телефон (861 обращение после апреля) бот не трогает вообще: там ноль записей с его результатом, что совпадает со словами администратора. Всего закрыто им 1667, передано людям 1021. До апреля бота не было ни в одном канале (`bot_result='нет'` для всего периода «до»).

```sql
SELECT channel, bot_result, COUNT(*)
FROM clean WHERE period = 'после' GROUP BY channel, bot_result ORDER BY channel, bot_result;
-- контроль: до апреля бота правда не было
SELECT COUNT(*) FROM clean WHERE period = 'до' AND bot_result != 'нет';
```

### 8. Время первого ответа до и после апреля — отдельно для письменных каналов и для телефона. Кто отвечает первым после апреля?

**Ответ:** Телефон почти не изменился: среднее 3.7 → 3.6 мин, медиана 3.1 → 3.0 (бот туда не ходит). Письменные каналы: было в среднем 64.0 мин при медиане 50.1, стало 0.4 мин. Но эти 0.4 — не скорость людей: после апреля первым в переписку отвечает бот-автоответ, и поле `first_reply_min` фиксирует именно его реплику. Проверка ниже: у обращений, которые бот сам закрыл ИЛИ передал человеку, время первого ответа одинаковое (0.4/0.4) — значит, человек на него не влияет. Вывод: судить об ускорении поддержки по цифре 0.4 нельзя; про людей можно говорить только по телефону (там без изменений) или по обращениям, где бота не было.

```sql
SELECT written, period, ROUND(AVG(first_reply_min), 1), ROUND(MEDIAN(first_reply_min), 1)
FROM clean GROUP BY written, period ORDER BY written, period;
-- у закрытых ботом и переданных людям первый ответ одинаковый — это автоответ, а не человек
SELECT bot_result, COUNT(*), ROUND(AVG(first_reply_min), 1), ROUND(MEDIAN(first_reply_min), 1)
FROM clean WHERE period = 'после' AND written = 1 GROUP BY bot_result;
```

## Возвраты

### 9. Сколько обращений переоткрыто и после скольких был возврат? Чем одно отличается от другого? Как это выглядит до и после апреля?

**Ответ:** Переоткрыто 579 обращений (`reopened=1`), возврат зафиксирован после 531 обращения (`came_back=1`). Разница в том, куда возвращается клиент: `reopened` — в то же самое обращение (его снова открыли в системе), а `came_back` — клиент завёл новое обращение с той же темой в течение недели после закрытия текущего. До апреля: переоткрытий 273 из 3211 (8.5%), возвратов 200 (6.2%). После: 306 из 3549 (8.6%) и 331 (9.3%). Переоткрытия почти не изменились, а возвраты выросли в полтора раза; при этом у обращений, которые бот закрыл сам, доля возвратов после апреля 12.1% против 6.9% у остальных — намёк, что «быстрое» закрытие не решает проблему. Но сравнивать аккуратно: возврат считается по совпадению темы, а у 152 строк с темой 'NULL' он технически не мог быть засчитан (проверено: там одни нули).

```sql
SELECT period, SUM(reopened), COUNT(*) FROM clean GROUP BY period;
SELECT period, came_back, COUNT(*) FROM clean GROUP BY period, came_back ORDER BY period;
-- доля возвратов по периодам и раскладка по результату бота после апреля
SELECT period, ROUND(100.0 * SUM(came_back) / COUNT(*), 1) FROM clean GROUP BY period;
SELECT bot_result, ROUND(100.0 * SUM(came_back) / COUNT(*), 1)
FROM clean WHERE period = 'после' GROUP BY bot_result;
-- контроль: у темы 'NULL' возврат не считается никогда
SELECT came_back, COUNT(*) FROM clean WHERE topic = 'NULL' GROUP BY came_back;
```

## Справочник

### 10. Сколько обращений вёл каждый сотрудник и сколько — без сотрудника? Есть ли в справочнике сотрудник без обращений? Как записан номер сотрудника в `clean` и в `agents`?

**Ответ:** Без сотрудника 1570 обращений (все — закрытые ботом). С сотрудником — 5190, их вели 18 человек; больше всех у ivan_p (с учётом дубля справочника JOIN удваивает его строки: 874 вместо реальных 437), дальше anna_k 457, irina_b 440. В справочнике 20 строк, но это не 20 людей: ivan_p записан дважды (id='1' встречается два раза), уникальных id — 19. Без обращений остался igor_h (id 19) — в выгрузке к нему не приклеено ни одного обращения. Номера записаны по-разному: в `clean` текст вида 'a12' (буква a + ноль впереди), в `agents` просто число '12'. Прямой JOIN `agent_id = id` даёт 0 строк — пришлось чинить через `substr(agent_id, 2)` и приведение к числу, и даже тогда из-за дубликата ivan_p счётчики по нему удваиваются.

```sql
SELECT COUNT(*) FROM clean WHERE agent_id IS NULL;
-- прямой джин не работает: форматы номеров разные
SELECT COUNT(*) FROM clean JOIN agents ON clean.agent_id = agents.id;
SELECT COUNT(DISTINCT agent_id) FROM clean WHERE agent_id IS NOT NULL;
SELECT COUNT(*), COUNT(DISTINCT id) FROM agents;
-- чиним ключ: отрезаем букву a и приводим к числу
SELECT a.login, COUNT(*) FROM clean c
JOIN agents a ON CAST(substr(c.agent_id, 2) AS INT) = CAST(a.id AS INT)
GROUP BY a.login ORDER BY 2 DESC LIMIT 5;
-- кто из справочника сидит без обращений
SELECT DISTINCT a.id, a.login FROM agents a
WHERE a.login NOT IN (
    SELECT a2.login FROM clean c
    JOIN agents a2 ON CAST(substr(c.agent_id, 2) AS INT) = CAST(a2.id AS INT));
```

## Промежуточный вывод

_Три утверждения, которые нельзя сделать по этой выгрузке сразу, хотя хочется. У каждого — число, которое это показывает._

1. «Время первого ответа упало с 64 минут до 0.4 — поддержка ускорилась в 160 раз». Нельзя: после апреля первым отвечает бот-автоответ, и `first_reply_min` = его реплика (у закрытых им и переданных людям цифра одинаковая — 0.4). Люди на телефоне отвечали 3.7 мин до и 3.6 после — никакого ускорения людей данные не показывают.
2. «Бот закрывает 62% обращений после апреля». Нельзя как точный факт: из нумерации пропущено 187 номеров (155 из них после апреля), то есть часть обращений просто не попала в выгрузку — знаменатель неполный, 62% это верхняя граница.
3. «Возвраты выросли из-за бота: было 200, стало 331». Нельзя сразу: доля возвратов считается по совпадению темы, а 152 строки с темой 'NULL' никогда не дают возврата (там came_back всегда 0); плюс 187 пропущенных номеров искажают сравнение периодов — рост мог быть частично артефактом выгрузки.
